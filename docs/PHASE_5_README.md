# Phase 5 — Smart Matching

## สิ่งที่ส่งมอบ

```
supabase/
  migrations/0020_phase5_matching.sql   (ใหม่ — ต้องรันบน Supabase)
  setup_all.sql                         (ต่อท้ายด้วย 0020 แล้ว)
  tests/phase5_matching.test.sql        (DB tests 10 กรณี)
src/lib/matching/
  score.ts          (คำนวณคะแนน — pure function)
  score.test.ts     (unit tests 10 กรณี)
  persist.ts        (โหลด candidate, บันทึก matches, audit log, notification)
  engine.ts         (server-only wrapper ที่ไม่ throw)
  queries.ts        (อ่าน match ของเจ้าของรายการ)
src/lib/actions/notifications.ts        (อ่านแล้ว / อ่านทั้งหมด)
app/notifications/page.tsx              (หน้าแจ้งเตือน)
app/dashboard/page.tsx                  (badge "อาจตรงกัน N รายการ")
app/dashboard/lost/[id]/page.tsx        (ส่วน "ประกาศพบของที่อาจตรงกัน")
src/components/nav.tsx, app/layout.tsx  (เมนูแจ้งเตือน + จำนวนที่ยังไม่อ่าน)
scripts/rematch-all.ts                  (npm run rematch)
```

## ขั้นตอนติดตั้ง

1. SQL Editor → รัน `supabase/migrations/0020_phase5_matching.sql`
2. ตรวจว่า `.env.local` มี `SUPABASE_SERVICE_ROLE_KEY` (ตัวเดียวกับที่ใช้ `npm run create-admin`)
   และตอน deploy ต้องตั้งค่าตัวนี้บน Vercel ด้วย — **ห้ามขึ้นต้นด้วย `NEXT_PUBLIC_`**
3. รัน `npm run rematch` หนึ่งครั้ง เพื่อจับคู่รายการที่แจ้งไว้ก่อน Phase 5

ถ้าไม่มี service role key การแจ้งของยังทำงานได้ตามปกติ แค่จะไม่มีการจับคู่ (มี log `[matching] ... failed` ฝั่ง server)

## คะแนน (เต็ม 100)

| เกณฑ์ | คะแนน | วิธีคิด |
|---|---|---|
| ประเภท | 30 | category เดียวกัน |
| สี | 15 | กลุ่มสีเดียวกัน (รองรับ ไทย/อังกฤษ เช่น ดำ = black) · สีใกล้เคียง (ฟ้า/น้ำเงิน, เงิน/เทา ฯลฯ) ได้ 8 |
| ยี่ห้อ | 15 | ยี่ห้อที่ผู้ทำหายระบุ ปรากฏในชื่อ/คำอธิบาย**สาธารณะ**ของผู้พบ (รองรับชื่อเรียกไทย เช่น ไอโฟน = Apple) |
| สถานที่ | 20 | location เดียวกัน |
| วันที่ | 10 | พบภายใน 1 วัน = 10 · 3 วัน = 7 · 7 วัน = 4 · 14 วัน = 2 |
| คำสำคัญ | 10 | ตัดคำภาษาไทยด้วย `Intl.Segmenter` แล้วเทียบคำที่ซ้ำกัน (ตัดคำทั่วไป/คำสีออก) |

- บันทึกเป็น match เมื่อได้ **≥ 40** · แจ้งเตือนเมื่อ **≥ 50**
- ผู้ใช้เห็นเป็นระดับ **ความเป็นไปได้สูง (≥70) / ปานกลาง (≥50) / ต่ำ** เท่านั้น ไม่เห็นตัวเลขหรือรายละเอียดคะแนน
- ตัดทิ้งอัตโนมัติ: ของที่ "พบ" ก่อน "หาย" เกิน 1 วัน, คนเดียวกันแจ้งทั้งสองฝั่ง, รายการที่ปิด/คืนแล้ว
- ค้น candidate ในช่วงวันที่ พบ ≤ 60 วันหลังหาย (สูงสุด 500 รายการต่อครั้ง)

## หลักความปลอดภัย

- **ฝั่งของที่พบใช้เฉพาะข้อมูลสาธารณะ** — ไม่อ่าน `secret_details`, `serial_number`, `exact_location`, `exact_time` เลย
  ถ้าใช้ข้อมูลลับในการคิดคะแนน ผู้ไม่หวังดีจะแก้รายการของหายของตัวเองไปเรื่อย ๆ แล้วดูคะแนนที่เปลี่ยน เพื่อเดาข้อมูลลับได้
  (มี test ยืนยัน: ใส่ "Apple" ไว้ใน `secret_details` ของผู้พบ คะแนนยี่ห้อยังเป็น 0)
- ผลแสดงเป็น "ความเป็นไปได้" เท่านั้น ข้อความในหน้าเว็บและแจ้งเตือนย้ำว่าไม่ได้ยืนยันความเป็นเจ้าของ
- แจ้งเตือนเฉพาะ**ผู้แจ้งของหาย** ไม่แจ้งผู้พบ · payload มีแค่ id และระดับความเป็นไปได้ ไม่มีข้อความจากฝั่งผู้พบหรือตัวตนผู้พบ
- ข้อมูลของที่พบที่แสดงในส่วน "อาจตรงกัน" ดึงจาก view สาธารณะ — เจ้าของรายการเห็นเท่ากับที่บุคคลทั่วไปเห็น
- `matches` / `notifications` / `audit_logs` เขียนได้เฉพาะ service role (ไม่มี INSERT policy ฝั่ง client)
- **0020 ปิดช่องเดิมจาก Phase 1:** ผู้ใช้เคยแก้ `title/message/payload/user_id` ของ notification ตัวเองผ่าน API ได้ ตอนนี้แก้ได้แค่ `is_read`
- anon ไม่มีสิทธิ์บน `matches` / `notifications`
- บันทึก `audit_logs` (`match.created`) ทุกครั้งที่เกิด match ใหม่

## ผลการตรวจคุณภาพ

- `npm test` — 36/36 (Phase 3: 17 · Phase 4: 9 · Phase 5: 10)
- typecheck / lint / build — ผ่าน
- DB tests Phase 3 / 4 / 5 บน PostgreSQL 16 — ผ่านทั้งหมด
- **Integration test กับ PostgREST จริง** (Postgres + PostgREST 12 + supabase-js):
  จับคู่ถูกเฉพาะ candidate ที่ควรได้ · รันซ้ำไม่เกิด match/แจ้งเตือนซ้ำ · รันจากฝั่ง found ไม่ซ้ำ ·
  แจ้งเตือนเฉพาะผู้แจ้งหาย ไม่มีข้อมูลลับ · re-score อัปเดตคะแนนโดยไม่แจ้งเตือนซ้ำ · audit log ครบ
- Render test หน้าที่ต้องล็อกอิน (dashboard / รายละเอียดของหาย / แจ้งเตือน) — ไม่มีข้อมูลลับของผู้พบหลุด

## ข้อจำกัด / งานต่อ

- ไม่เปลี่ยนสถานะรายการเป็น `matched` อัตโนมัติ (เพราะสถานะแสดงบนหน้าสาธารณะ) — จะใช้ใน flow claim ของ Phase 6
- ถ้าคะแนนของคู่เดิมลดลงต่ำกว่า 40 ภายหลัง (เช่นแก้รายการผ่าน API) match เดิมยังอยู่ — admin จัดการได้ใน Phase 10
- สถานที่ให้คะแนนแบบตรงกันเท่านั้น ยังไม่มีข้อมูล "อาคารใกล้เคียง"
