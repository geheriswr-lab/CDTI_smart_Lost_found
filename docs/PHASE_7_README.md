## สัญญาณความเสี่ยง (risk_events)

ทำงานเป็น trigger บนตาราง `claims` — ข้ามไม่ได้จากฝั่ง client และไม่ขึ้นกับว่าเปลี่ยน claim ผ่านช่องทางไหน

| สัญญาณ | เงื่อนไข | ระดับ |
|---|---|---|
| ส่งคำขอรับของถี่ | ≥ 5 คำขอใน 7 วัน | ปานกลาง (≥ 8 = สูง) |
| คำขอไม่ผ่านการตรวจสอบหลายครั้ง | ผล "ข้อมูลไม่พอ"/"ปฏิเสธ" ≥ 3 ครั้งใน 30 วัน | ปานกลาง (≥ 5 = สูง) |
| ส่งคำขอซ้ำกับรายการเดิม | ส่งครั้งที่ 2 / 3 ของของชิ้นเดียวกัน | ต่ำ / ปานกลาง |
| คำตอบต่างจากครั้งก่อน | ≥ 2 ข้อขัดแย้งกับครั้งก่อน (การเพิ่มรายละเอียดไม่นับ) | ปานกลาง |
| บัญชีใหม่ขอรับของมูลค่าสูง | บัญชีอายุ < 7 วัน + หมวดมูลค่าสูง | ปานกลาง |

- สัญญาณเดียวกันของคนเดิมใน 7 วัน **ไม่สร้างซ้ำ** แต่ปรับระดับขึ้นได้
- details เก็บแค่ตัวเลข/ชื่อช่อง **ไม่เก็บข้อความคำตอบ**
- สัญญาณเป็นแค่ "ให้คนดู" — **ระบบไม่ตัดสินหรือลงโทษอัตโนมัติ**

## คำเรียกที่เป็นกลาง (บังคับที่ DB)

- `event_type` ได้เฉพาะ 5 ชนิดข้างบน
- `resolution` ได้เฉพาะ: `needs_review` (Needs Review) · `suspicious_activity` (Suspicious Activity) · `cleared` · `account_restricted`
- ลองบันทึก "thief" หรือ "scammer_detected" → DB ปฏิเสธ (มี test)
- มี unit test สแกนคำใน UI ทั้งหมด ห้ามมีคำอย่าง โจร/ขโมย/มิจฉาชีพ/ทุจริต/fraud/scam

## ข้อพิพาท (Dispute)

```
คำขอที่ 2 เข้ามา (หรือมีคนส่งใหม่) ขณะที่มีคำขออื่นเปิดอยู่
  → คำขอที่เปิดอยู่ทั้งหมดของของชิ้นนั้น = disputed
  → แจ้งเตือนเจ้าหน้าที่ทุกคน + audit log
  → อนุมัติไม่ได้ (CLAIM_DISPUTED) จนกว่าจะเหลือคำขอที่เปิดอยู่รายการเดียว  ← = ระงับการส่งมอบ
  → เจ้าหน้าที่ตรวจเทียบ แล้วบันทึก "ข้อมูลไม่พอ"/"ปฏิเสธ" ให้คำขอที่ไม่ผ่าน → อนุมัติคำขอที่เหลือได้
```

- ผู้ขอ**ไม่รู้**ว่ามีคนอื่นขอ — เห็นแค่ "อยู่ระหว่างตรวจสอบ" และไม่ได้รับแจ้งเตือนเรื่องข้อพิพาท
- ผู้ขอถอนตัวจากข้อพิพาทได้ (ยกเลิกคำขอ)
- หน้า admin: การ์ดจำนวนข้อพิพาท, แท็บ "ข้อพิพาท" ในคิวคำขอ, แถบแดงในหน้าตรวจสอบพร้อมลิงก์ไปคำขออื่น, ปุ่มอนุมัติถูกซ่อน

## การจัดการสัญญาณ

- **เจ้าหน้าที่ (staff/admin):** บันทึกผล ต้องตรวจสอบ / เฝ้าระวัง / ไม่พบปัญหา + บันทึกภายใน — ผ่าน `resolve_risk_event()` (audit)
- **admin เท่านั้น:** จำกัดสิทธิ์ / ยกเลิกการจำกัดสิทธิ์บัญชี ผ่าน `set_account_restriction()` — ต้องใส่เหตุผล
  - สัญญาณที่เปิดอยู่ของผู้ใช้นั้นปิดเป็น `account_restricted`
  - ผู้ใช้ได้รับแจ้งเตือนแบบกลาง ๆ · เหตุผลเก็บใน risk_events (staff-only) ไม่ใส่ใน audit log
  - บัญชีที่ถูกจำกัดแจ้งรายการ/ขอรับของไม่ได้ (กฎจาก Phase 3/6)
- จัดการสัญญาณหรือจำกัดสิทธิ์ **ตัวเอง** ไม่ได้
- ผู้ใช้สร้างหรือแก้สัญญาณเองไม่ได้ (ไม่มีสิทธิ์ตาราง และเรียก `raise_risk_event` ไม่ได้)
